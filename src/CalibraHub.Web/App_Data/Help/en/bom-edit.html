The Bill of Materials (BOM) editor is where you define a product's component list. Each line states one component required to build the product, and how much of it.

Header

  • Product (the item this recipe belongs to) and, if any, its combination (variant).

Component lines

  • Each line carries a component, a quantity, a unit and a scrap ratio.
  • If a component is a semi-finished item it has its own recipe — the tree goes deeper.
  • Fast entry: Enter chains to the next line; Excel paste and undo are supported.

Scrap is a RATIO, not a quantity. Enter 0.05 for 5% scrap; the explosion computes quantity × (1 + scrap). Entering 5 for "5%" would mean 500% scrap.

The BOM Tree tab

Shows every level of the product in one place and lets you edit it there. When you pick a semi-finished component, its stored recipe is loaded into the tree so you can change it directly.

Two independent kinds of "variation"

  • Combination — the material itself differs (red body vs blue body). Chosen with the + Combination button on the line. Each combination has its own base recipe.
  • Recipe version — same material, different way of making it (same body, different connector). The line is pinned to a version.

The two combine: "the blue body, built with the recipe customised for PRODUCT-01."

Shared sub-recipes and automatic versioning

If a semi-finished item's recipe is used by more than one product, the line shows a Shared ×N badge. Editing such a sub-recipe in the tree does not overwrite it in place — that would silently change the other products too.

Example. TABLE and CABINET both use the LEG-SET semi-finished item:

Before
  LEG-SET (base)  →  screw ×4
  TABLE   → LEG-SET   (follows base)
  CABINET → LEG-SET   (follows base)      Badge: Shared ×2

"shim ×2" added to LEG-SET inside TABLE's tree, then saved
  LEG-SET (base)    →  screw ×4            ← UNCHANGED
  LEG-SET "TABLE"   →  screw ×4, shim ×2   ← new version
  TABLE   → LEG-SET ["TABLE" version]      ← pinned
  CABINET → LEG-SET (follows base)         ← UNAFFECTED

After saving, a banner reports that a version was derived. To see which version is tied to which products, click the Shared or Usage badge on the line: every recipe of that semi-finished item (base plus versions) is listed together with the products using it.

Same content a second time: no new version

If you make the same customisation under another product, a second version is not created — the line is bound to the existing version instead, and the banner says so. 

"shim ×2" also added to LEG-SET inside CABINET's tree
  LEG-SET "TABLE"   →  screw ×4, shim ×2   ← NO NEW VERSION
  TABLE   → LEG-SET ["TABLE" version]
  CABINET → LEG-SET ["TABLE" version]      ← bound to the same version

Why this matters: it is not just about saving records. When cumulative work orders are created, demand is grouped by recipe. Had the same content lived in two separate versions, the same job would be split into two work orders. One version → one work order.

When the semi-finished item is used by a single product

No version is derived; the base recipe is edited directly — there is nobody else to protect. A version only becomes meaningful once a second consumer appears. In other words, "being customised" is not a separate flag: it is the line being pinned to a version.

Cycle protection

A material cannot be its own component, directly or indirectly. The tree catches this before saving, names the chain (TABLE → LEG-SET → TABLE) and marks the row where the cycle closes in red. Such a tree cannot be saved.

Saving

  • Save Tree writes only the nodes that actually changed; untouched sub-recipes are left alone.
  • Save stores the header and component list; Back returns without saving.

Note: when a work order is released, this recipe is exploded into component requirements and sub-assemblies. The pinned version on the line is copied onto the work order component, so the work order carries the recipe it was built from — later recipe changes do not distort past orders.
